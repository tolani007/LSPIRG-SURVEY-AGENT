Core Concepts

Arrays, Strings, and the Two-Pointer Technique

An array is a row of numbered boxes. Box 0, Box 1, Box 2, and so on. You can jump to any box instantly if you know its number. That is O(1) access. The catch: inserting or removing a box in the middle means shifting everything after it.

Most array problems on LeetCode come down to two patterns: two pointers (one at each end, walking inward) or sliding windows (a movable frame over a portion of the array). The trick is always the same: can you avoid looking at every element more than once?

Key Insight: Strings are just arrays of characters. If you can solve array problems, you can solve string problems. The data structure is identical; only the interpretation changes.

Hash Maps (The Most Important Data Structure)

A hash map is like a coat check. You hand over your coat (value) and get a ticket number (key). Later, you show the ticket and get your coat back instantly. In Python, this is a dictionary.

The magic: lookup, insertion, and deletion are all O(1) on average. Whenever a problem says "find if X exists" or "count occurrences," a hash map is almost always the answer.

The classic example is Two Sum. Given an array, find two numbers that add to a target. Without a hash map, check every pair: O(n squared). With a hash map, for each number, check if (target minus number) is already in the map. One pass. O(n). Beautiful.

Trees and Graph Traversals

A tree is a family tree. One root at the top, children branching down. A binary search tree adds an ordering rule: everything left is smaller, everything right is larger. This makes searching O(log n), because at each node you eliminate half the remaining candidates.

A graph is a map of cities and roads. The two fundamental traversal algorithms are BFS (explore all neighbors before going deeper, like ripples on a pond) and DFS (go as deep as possible before backtracking, like exploring a maze).

Key Insight: BFS finds the shortest path in unweighted graphs. DFS is better for detecting cycles, topological sorting, and exploring all possibilities. Choosing between them is one of the most common interview questions.

Dynamic Programming

DP is the art of not solving the same problem twice. Imagine climbing a staircase where you can take 1 or 2 steps. How many ways can you reach step 10? You could recursively try every combination, but you will re-calculate "ways to reach step 5" dozens of times.

DP says: calculate it once, store the result, and look it up later. The two approaches are top-down (recursion with memoization) and bottom-up (iteration from the base case). The hard part is seeing the substructure: can I express the answer for size N in terms of answers for smaller sizes?

Stacks, Queues, and Heaps

A stack is a stack of plates: last in, first out. A queue is a line at a coffee shop: first in, first out. These simple structures power surprisingly complex algorithms. Stacks are behind every function call in your program. Queues power BFS. When you see "process things in order," think queue. When you see "match things in reverse order," think stack.

A heap is like an ER waiting room. The most urgent patient goes first. In a min-heap, the smallest element is always at the top. Insertion and extraction are both O(log n). Use it for "find the K largest elements" or "merge K sorted lists."

Step 1: Read the problem carefully. Understand what input you are given and what output is expected. Identify constraints like array size and value range.

Step 2: Identify the pattern. Is this a sliding window problem? A BFS? A DP? Recognizing the pattern is 80% of the work.

Step 3: Plan before coding. Write pseudocode. Choose your data structure. State your expected time complexity.

Step 4: Implement in Python. Use built-in data structures: lists, dicts, sets, heapq, deque.

Step 5: Test with examples, then think of edge cases. Empty input, single element, all duplicates, maximum size.

Step 6: Document the reasoning. This is what makes my repo different from a solution dump.

What I Learned

  1. Pattern recognition is the real skill. After enough problems, you start seeing categories. "Oh, this is a sliding window problem." "This is BFS on an implicit graph." That pattern library is invaluable in interviews and in real engineering.
  2. Algorithmic thinking changes how you write all code. The ability to reason about time and space complexity improves every function you write, not just interview solutions.
  3. Python fluency compounds. List comprehensions, dictionary tricks, itertools, heapq, collections.deque. Daily practice makes you genuinely fast in Python.
  4. Every hard problem is made of easy subproblems. Learning to decompose is the most transferable skill in computer science.
  5. Practice builds calm. When you have solved hundreds of problems, a whiteboard interview feels like a conversation, not an exam.
  6. There is genuine joy in elegance. Finding a clean, efficient solution produces a thrill that keeps me coming back.

Why This Matters for Your Career

Technical interviews are conversations about how you think. This practice prepares you for the most common lines of questioning.

Q: Explain the time complexity of your solution.

Always state Big-O for both time and space. Walk through the analysis: "I have one loop over N elements, and inside the loop I do a hash map lookup which is O(1), so the total is O(N) time and O(N) space for the hash map."

Q: Can you solve this without extra space?

This asks if you can go from O(N) space to O(1). Techniques: two pointers, in-place array modification, bit manipulation, or mathematical formulas. Not always possible, but always worth considering.

Q: What data structure would you use for this problem?

Connect the problem's requirements to the data structure's strengths. Need fast lookup? Hash map. Need sorted order with fast insert? Balanced BST. Need FIFO processing? Queue. Need to repeatedly extract the minimum? Heap. Justify with Big-O.

Q: Walk me through your approach before you start coding.

State the problem in your own words. Identify the pattern. Sketch the algorithm in plain English. State expected time and space complexity. Then start coding. Interviewers care about your thought process as much as your code.

Q: What if the input is very large, say 10 million elements?

O(n squared) is out. You need O(n log n) or O(n). Think about streaming solutions that process elements one at a time. Consider external sorting, MapReduce, or approximation algorithms. Show that you think about real-world constraints.

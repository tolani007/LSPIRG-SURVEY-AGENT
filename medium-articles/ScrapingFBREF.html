How I Built an Ethical Web Scraper for Premier League Football Data

Rate limiting, exponential backoff, checkpoint recovery, and a Flask UI: building a production-grade data pipeline from scratch with Python and BeautifulSoup.

11 min read

Every data science interview will eventually ask you: "Where did your data come from?" If your answer is "I downloaded a Kaggle CSV," that is fine. But if your answer is "I built a production-grade scraper with rate limiting, exponential backoff, checkpoint recovery, and a web interface," now you are showing engineering maturity.

I needed Premier League match data for my predictive modeling project. Lots of it. Multiple seasons of shooting stats, passing stats, defensive stats, and possession stats. The best free source lives on FBref.com. But copying and pasting hundreds of tables by hand? That is not analytics. That is punishment.

So I built a scraper. Not a quick-and-dirty script, but a resilient data pipeline that respects the website, handles failures gracefully, and even has a browser-based UI. This project became the foundation for everything else in my sports analytics portfolio.

Why I Built This

If you want to do serious football analytics, you need data. The question is how you get it. I wanted a system that could pull multiple seasons of comprehensive statistics and package them into clean CSV files, ready for analysis or model training.

But I also wanted to build it the right way. That meant being polite to the server, handling every failure mode I could think of, and making it usable by someone who has never touched a command line. The result is a full ETL pipeline disguised as a web scraper.

The Core Concepts

HTML Parsing with BeautifulSoup. HTML is a tree structure. Think of a family tree: the <html> tag is the great-grandparent, <body> is the grandparent, <div> tags are parents, and the actual data is the children. BeautifulSoup lets me navigate this tree. I can say "find the table with class 'stats_table'" and it goes straight to it, like knowing exactly which branch of the family tree holds the data I need.

soup = BeautifulSoup(html_content, 'html.parser')
table = soup.find('table', {'class': 'stats_table'})

Two lines and I have grabbed a whole stats table.

Key Insight: The real engineering challenge is not parsing HTML. It is building a system that handles failures gracefully, respects the server, and can resume after interruption. The scraper itself is maybe 20% of the work. The resilience layer is the other 80%.

Rate Limiting. Imagine you are at a library and you keep asking the librarian for books, one after another, nonstop. Eventually she is going to get annoyed and kick you out. Websites work the same way. If you hit FBref with 100 requests per second, they will block your IP. Rate limiting means I deliberately slow down my requests. I am being polite. I am waiting my turn.

Exponential Backoff. When the website says "slow down" (a 429 status code), I do not just wait a fixed amount of time. First retry: wait 2 seconds. Second retry: wait 4 seconds. Third retry: wait 8 seconds. Each time, I double the wait. This is an industry-standard pattern used in AWS SDKs, gRPC, and every serious retry library.

for attempt in range(max_retries):
    response = requests.get(url)
    if response.status_code == 200:
        break
    wait_time = base_delay * (2 ** attempt)  # 2, 4, 8, 16...
    time.sleep(wait_time)

Checkpoint Recovery. Imagine writing a 50-page paper and your computer crashes at page 47. Without saving, you start from scratch. With a checkpoint system, you pick up at page 47. My scraper saves its progress to scraper_checkpoint.json after each successful batch. If it crashes, gets rate-limited, or I just close my laptop, it knows exactly where to resume.

Rotating User-Agent Headers. Every browser request includes a User-Agent string that identifies it. If a scraper sends the same ID every time, the website notices. Using fake-useragent, I rotate through different browser identities. One request looks like Chrome on Windows. The next looks like Firefox on Mac. It is about making my traffic look like normal, diverse web traffic.

How It Works

The whole project is really an ETL pipeline. Extract data from FBref via HTTP requests. Transform it from raw HTML into structured DataFrames using BeautifulSoup and pandas. Load the clean data into CSV files ready for downstream analysis.

  Configuration       Request Phase         Parsing Phase        Output
  +------------+     +--------------+      +--------------+    +----------+
  | Seasons    |     | HTTP GET     |      | BeautifulSoup|    | Clean    |
  | Teams      | --> | + User-Agent | ---> | HTML -> Table| -> | CSV      |
  | Stat Types |     | + Rate Limit |      | + pandas     |    | Files    |
  +------------+     | + Backoff    |      +--------------+    +----------+
                     +--------------+             |
                           |                      v
                     +--------------+      +--------------+
                     | 429 / Error? |      | Checkpoint   |
                     | Retry w/     |      | Save to JSON |
                     | Backoff      |      +--------------+
                     +--------------+

Between each request, the scraper waits. If it gets a 429 or 5xx error, exponential backoff kicks in. After each successful batch, it writes its current position to the checkpoint file. Individual team and season DataFrames get merged and concatenated into comprehensive datasets. And the Flask app wraps the whole process in a browser-friendly interface with real-time progress updates.

What I Learned

  1. HTTP fundamentals are essential. Status codes (200, 403, 429, 500), headers, request/response cycles. These are the backbone of the internet, and understanding them made me a better engineer across the board.
  2. Defensive programming saves you. What happens when things go wrong? Rate limits, connection timeouts, malformed HTML. My code handles all of it. This mindset transfers to every production system I have built since.
  3. ETL is a universal pattern. Extract, Transform, Load. This is the pattern behind every data engineering job. The scale changes, but the architecture stays the same. Replace HTTP requests with Kafka consumers, replace CSV with a data warehouse, and you have enterprise ETL.
  4. State management matters. The checkpoint system taught me to think about idempotency and crash recovery. These are the same concepts behind database transaction logs and ML training checkpoints.
  5. Respectful scraping is non-negotiable. Checking robots.txt, implementing rate limiting, and respecting terms of service. The ethics matter, both legally and professionally.
  6. Production-mindset coding is different. This is not a notebook experiment. It has error handling, logging, configuration, and a UI. That gap between "works in a notebook" and "works reliably" is where engineering maturity lives.

Why This Matters for Your Career

This project covers topics that come up constantly in data engineering and backend interviews. Here are the questions it prepares you for:

"How would you design a web scraper that needs to run reliably over hours?" Talk about the checkpoint system. Explain that any long-running process needs to be resumable. Mention idempotency: the ability to restart without duplicating work.

"What is exponential backoff and when would you use it?" Explain the doubling wait pattern. Mention it is standard in distributed systems. The key insight: it prevents thundering herd problems where many clients retry simultaneously and overwhelm the server.

"Describe an ETL pipeline you have built." Walk through Extract (HTTP requests to FBref), Transform (BeautifulSoup parsing, pandas cleaning), Load (CSV export). Mention that this pattern scales to enterprise systems.

"How do you make a data pipeline fault-tolerant?" Checkpointing, retry logic with backoff, graceful error handling, and logging. The scraper can crash at any point and resume without data loss or duplication.

"Tell me about a time you built something beyond a Jupyter notebook." This project has a Flask web UI, modular Python scripts, a checkpoint system, and handles real-world failure modes. It is production-adjacent, not just exploratory.

Try It Yourself

Clone the repo and try it out. You can run the scraper directly from the command line or launch the Flask web UI.

git clone https://github.com/tolani007/ScrapingFBREF.git
cd ScrapingFBREF
pip install -r requirements.txt

# Run the scraper directly
python fbref_scraper.py

# Or launch the Flask web UI
python app.py
# Then open http://localhost:5000 in your browser
